## 議論 / Discussion

- 「最新の情報を確定して記録する」の「確定」をどう解釈するか。
  - 決定まで確定して `ledger/events/` に追記すると、Signity の中核原則（人間承認必須）に反する。
  - → 確定度を 3 層に分けた。L1 Observed（AI が確定してよい）/ L2 Candidate（AI は提示のみ）/
    L3 Approved（人間のみ）。ループが確定するのは L1 だけ。
- 「決まったこと」だけを出すか、三分類にするか。
  - 実務で滞留を生むのは「決まったつもりで、主体・期日・範囲のどれかが欠けているもの」。
  - → 「決まったこと / 決まっていないこと / 決まったつもりのもの」の三分類にし、
    3 つ目の可視化を主目的とした。横断で「返していない球」も出す。
- Mac のローカル情報をどう取るか。
  - リモートから直接は取れない。Drive 同期・ローカルエージェント・push の 3 案。
  - → Mac 側の launchd が前日更新ファイルを `docs/journal/inbox/D/` へ push する方式にした。
    その 10 分後に起動するリモートのループが、その push を読む。
- コネクタのないメッセンジャー / SNS をどうするか。
  - → 「読めないものを読めたことにしない」。通知メール転送（Gmail ラベル `Signity/Inbox`）か
    inbox への手動投下で橋渡しし、取得できなかったソースは `scan.json` に
    `status: unavailable` として必ず記録する。
- 業務の生ログを Git に蓄積してよいか。
  - → よくない。`AGENTS.md` 3 章の延長として、journal には参照（permalink / message id / file id）と
    要約だけを書く。機微な記述は `[機微：参照のみ]` として参照だけ残す。
- 起動時刻。要望末尾の「10:30」が就寝時刻（22:30）なのか、発言時刻（10:30）なのかが判然としなかった。
  発言時刻は 10:36 JST であり、後者の可能性が高いと見て人間に確認した。
  - 22:30 起動・当日対象だと、22:30〜24:00 に確定した話が翌日の窓に落ちる。
  - 01:00 起動・前日対象だと、対象日の丸一日を 1 つの記録に収められる。
    代わりに実行日と対象日が 1 日ずれ、Mac がスリープ中だとコレクタが遅れる。
  - → **人間が 01:00 JST（cron `0 16 * * *` UTC・対象は前日）を選択した。**
    Mac 側コレクタは 00:50 JST に `--yesterday` 付きで走る。
- 01:00 起動にすると、ループは実行時点から見て「過去日」のファイルに書くことになる。
  `docs/journal/README.md` の「過去日を書き換えない」に抵触しないか。
  - → ループは対象日 `D` の当日運用の締めくくりであって遡及ではない、と位置づけた。
    人間が `D` 中に書いた記述は書き換えず、末尾に追記するだけ。
    `D+2` 以降に `D` のファイルへ書くことはしない。
