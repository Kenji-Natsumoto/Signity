## 4. UTM 設計

すべての外部リンクに付けます。付け忘れた投稿は**測定対象外として記録**します（推測で埋めない）。

```text
https://jp.viberush.io/?utm_source=<source>&utm_medium=<medium>&utm_campaign=jp-bip-smoke-2026-09&utm_content=<YYYYMMDD>-<NN>
```

| パラメータ | 値 |
| --- | --- |
| `utm_source` | `x` / `note` / `linkedin` / `youtube` |
| `utm_medium` | `social`（投稿本文）/ `profile`（プロフィール欄のリンク） |
| `utm_campaign` | `jp-bip-smoke-2026-09`（期間中は固定） |
| `utm_content` | 投稿日 + その日の連番（例 `20260914-01`）。カレンダーの行と 1 対 1 で対応させる |

例:

```text
X 09-14 の 1 本目
https://jp.viberush.io/?utm_source=x&utm_medium=social&utm_campaign=jp-bip-smoke-2026-09&utm_content=20260914-01

LinkedIn プロフィール欄
https://jp.viberush.io/?utm_source=linkedin&utm_medium=profile&utm_campaign=jp-bip-smoke-2026-09&utm_content=profile-01
```

**前提（未確認）**: UTM が意味を持つのは、jp.viberush.io 側で流入を記録できる場合だけです。
解析基盤がない場合は、次のいずれかに切り替えてください。

- 掲載フォームに「どこで知ったか」の任意項目を 1 つ足す（最も確実。実装が必要）
- 投稿ごとに異なる短縮 URL を使い、短縮側のクリック数を数える（掲載への転換は追えない）

## 6. 判定基準

2026-09-25 の集計後、次のように扱います。

| 観測 | 扱い |
| --- | --- |
| LinkedIn の 1 投稿あたり掲載数が X を上回った | `DE-20260911-001` の `revisit_triggers[0]` が発火。**配分を変更する新しい Decision Event を起案する**（Draft の編集や Correction ではない） |
| X の 1 投稿あたり掲載数が最大だった | 仮説が支持された。配分は維持し、次は絶対量を増やす判断に移る |
| どのチャネルも新規掲載が 0〜1 件 | チャネルの問題ではなく、**掲載までの導線か提供価値の問題**として切り分ける。チャネル配分を動かしても解決しない |
| サンプル不足（各チャネル 2 本未満、X が 14 本未満） | **判定しない。** 期間を延長し、延長したこと自体を journal に記録する |
| 第 1 週と第 2 週で差が出た | **チャネルの差として読まない。** 09-19〜09-23 の 5 連休が交絡している |

1 投稿あたり掲載数が同等（差が 1 件未満）なら、**判定せず維持**します。
2 週間・各 2 本では LinkedIn の差を検出できる統計的な力がないため、この規模で出る差は
方向の示唆までです。確定的な結論として Decision Event に書かないでください。
